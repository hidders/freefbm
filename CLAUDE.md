# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm install        # Install dependencies
npm run dev        # Start dev (Vite on :5173 + Electron, with DevTools)
npm run build      # Bundle with Vite then package with electron-builder → release/
npm run preview    # Preview the Vite production build
```

No test runner or linter is configured.

## Architecture

This is an **Electron desktop application** for editing ORM2 (Object-Role Modeling 2) conceptual diagrams. The UI renders entirely in SVG on a pannable/zoomable canvas.

### Process split

- **Electron main** (`electron/main.cjs`) — window lifecycle, native menus, file dialogs (`.ffbm` JSON files; `.orm2`/`.json` still open; NORMA `.orm` is imported)
- **Preload** (`electron/preload.cjs`) — exposes `window.electronAPI` (openFile, saveFile, onMenuEvent) via context bridge
- **Renderer** — React 18 SPA served by Vite; communicates with main only through `window.electronAPI`

### State management

All application state lives in a single **Zustand store** (`src/store/ormStore.js`). This includes:
- ORM2 element data: `objectTypes`, `facts`, `subtypes`, `constraints`
- Interaction state: `selectedTool`, `selectedId`, `linkDraft` (multi-step operations), `pan`, `zoom`
- Undo/redo stacks: JSON snapshots, max 60 history entries (managed by `src/hooks/useUndoRedo.js`)

### ORM2 data model

| Element | Shape | Key fields |
|---|---|---|
| ObjectType | rect (entity) or ellipse (value) | `name`, `isValueType`, `x`, `y` |
| FactType | row of role boxes | `roles[]` (each has `objectTypeId`, uniqueness constraints) |
| Subtype | arrow between ObjectTypes | `superTypeId`, `subTypeId` |
| Constraint | graphical badge | `type` (Exclusion/Equality/Subset/Ring/Frequency), `roleGroups[]` |
| Group | none (colours its members) | `name`, `colors{outline,fill,text,graphics,floating,constraint,deontic,connector}` (NORMA colour roles), `priority`, `members[]` (element, role or note ids); see `src/utils/groups.js` |
| Schema | none (schema strip above the diagram tabs) | `name`, `profile` (`orm2` or `relational`); elements and diagrams carry `schemaId`, the active schema is the active diagram's; panels use `scopeToSchema`/`useScopedStore`. A relational schema is encoding B (table = entity type, column = binary fact type to a value type, see docs/logic/schema-mappings.tex), checked by the Relational Profile validation category, with PostgreSQL datatypes |
| Mapping | none (Mappings tab in the bottom panel) | `name`, `sourceSchemaId`, `targetSchemaId`, `rules[]` of `{name, source, target}`; each side is a pattern in the rule-tree format (∃, ∧, fact, type, `x ≈ $y`/`x ≈ 'c'` as vcmp, table row `rel`, optional `opt` [$y], `not`); see `src/mapping/mapping.js` and docs/logic/schema-mappings.tex |
| PropertyDefinition | none (values in each element's `properties`) | `name`, `category`, `type` (string/number/boolean/date/enum), `options`, `default`, `appliesTo[]`; see `src/utils/customProperties.js` |

Roles connect FactTypes to ObjectTypes; `RoleConnectors.jsx` draws the SVG lines.

### Component responsibilities

- `App.jsx` — mounts all panels, registers global keyboard shortcuts, calls `useElectronMenu`
- `Canvas.jsx` — SVG viewport; owns mouse/wheel events, drag, pan, grid snapping
- `ObjectTypeNode.jsx` — entity/value rendering + drag + subtype/role link initiation
- `FactTypeNode.jsx` — n-ary fact box + uniqueness constraint toggle
- `Inspector.jsx` — right-panel property editor for the selected element
- `useElectronMenu.js` — translates Electron menu IPC events (New, Open, Save, Undo, Redo…) into store actions

### Tool modes

The active `selectedTool` in the store determines how canvas clicks are interpreted: `select`, `addEntity`, `addValue`, `addFact`, `assignRole`, `addSubtype`, `addConstraint`.

### File format

Files are saved as `.ffbm` (JSON; the legacy `.orm2` and `.json` extensions still open). The store's `exportModel()` / `importModel()` functions serialise/deserialise all four element collections.

File › Import PostgreSQL DDL… reads a `.sql` script into a new relational schema of the open file (`src/relational/ddlParse.js` parses CREATE TABLE / ALTER TABLE ADD CONSTRAINT and ADD/DROP/RENAME/ALTER COLUMN / enums / domains / unique indexes; `ddlImport.js` builds encoding B with one diagram, as one undo step via `store.historyBatch`); File › Export PostgreSQL DDL… writes the active relational schema (`ddlExport.js`).

A diagram of a relational schema can be drawn as an ERD (crow's foot, read-only): the ORM2 | ERD switch at the right of the diagram tabs sets `diagram.notation`; `src/components/ErdView.jsx` draws the tables that `src/relational/relationalModel.js` reads from encoding B (shared with the DDL export), with box positions in `diagram.erdPositions` (Auto layout clears them); `src/relational/erdRouting.js` places tables in columns by FK depth and routes FK lines at right angles around the boxes, one attachment point per FK end (assignPorts); clicking a line selects the FK's subset constraint and highlights its columns.

Mappings (workbench step 7): `src/mapping/mapping.js` holds the pattern format, its flat form (`treeToSide`), the expansion of table-row atoms into encoding B (`expandSide`), and `checkRule` (well-formedness, types, the P2 binding rules for frontier variables, key-safety via `determined`); the Mappings tab (`MappingsTab.jsx`) lists mappings and their rules as formulas with check messages, and rules are edited live in the floating `MappingRuleEditor.jsx` (`store.mappingRuleEditor`), a pattern mode of the derivation rule editor's click-to-select tree editing (it reuses VarSelect/ConstInput from `DerivationRuleEditor.jsx`). Mappings are saved in the file (`schema.mappings`) and are part of undo.

Basic and Advanced mode (the switch at the top of the tool panel, `store.advancedMode`, kept in localStorage `freefbm.advancedMode`): in Basic mode mappings come only from Generate, Guess and Fold, the Mappings tab shows rules read-only (no Add mapping, + Rule, Edit or reordering; a rule with errors offers Drop rule), and `openMappingRuleEditor` scrolls to and highlights the rule (`store.mappingRuleFocus`) instead of opening the editor. Advanced mode keeps hand editing.

Mapping diagrams (workbench step 7b): a diagram with `mappingId` draws that mapping; it belongs to the mapping's source schema (`schemaId`, where new elements go) but may hold occurrences of both schemas (`activeScopeIdsOf`/`scopeToSchema` then scope panels to both). The schema strip lists mappings as chips and the Mappings tab has a Diagram button; both call `store.openMappingDiagram`, which makes the first diagram with the elements the rules name (`addMappingRuleElements`: home positions from each schema's own diagrams, target side to the right). `src/components/MappingLayer.jsx` tints elements by side (MappingTints) and draws each rule as a node linked to its elements (MappingRules; hover highlights via `store.ruleHighlight`, click opens the rule editor, drag stores `diagram.mappingRulePositions`). Mapping diagrams are always drawn in ORM2.

Running mappings (workbench step 8): `src/mapping/runMapping.js` matches one side of each rule against its schema's population (`matchSide`, backtracking with fact indexes; opt binds $y to null, not filters) and builds the other side's population (`buildSide`: entity instances come from their reference schemes, ref mode or composite identifier, so the same key gives the same instance; identifying facts are not stored as tuples). `runMapping(state, mapping, 'forward'|'backward')` returns the built populations with per-rule match counts and a log; `withRunApplied` swaps them into the target schema (`store.applyMappingRun`, one undo step); `roundTrip` runs there and back and compares each type and fact population of the source (lost/gained, plus types and facts no rule reads). The Mappings tab has Run →, Run ← and Round trip buttons. Sample rows come from `INSERT … VALUES` statements in an imported DDL script (`ddlParse` `inserts`, `ddlImport.samplePopulation`, max 20,000 rows); `COPY` blocks are not read.

Guessing an ORM2 schema (workbench step 9): `src/relational/guessOrm.js` reads a relational schema (`relationalModel`) back as ORM2 and writes the mapping to it. `analyseTables` classifies each table (entity, subtype when its primary key is a foreign key to another table's key, junction when all columns are in its foreign keys and its key and nothing references it, nokey) and finds surrogates (a one-column key with generated values: SERIAL, IDENTITY, a sequence or UUID default) and natural keys (UNIQUE, NOT NULL, not generated); `guessOrmSchema` builds entity types (singular Pascal-case names), reference modes or preferred external uniqueness constraints, attribute and foreign-key fact types (readings from column names), m:n fact types, and one mapping rule per entity type, attribute and foreign key, joining over a dropped surrogate in the source pattern. The dialog `GuessOrmDialog.jsx` (store `guessOrmDialog`, opened from the schema strip's + menu) lets the user keep or drop each surrogate; `store.guessOrmFromRelational` adds schema, diagram (rows by foreign-key depth) and mapping as one undo step. When a run builds a table whose surrogate nothing gives, `runMapping` invents it from another key (`⟨values⟩`, `altKeysOf`), and `roundTrip` compares such surrogates up to renaming (`surrogateRenaming`). The invented key is the same in every rule (`prepareRun` → `inventKeys`); `prepareRun`/`executeRun` split a run so it can be repeated cheaply on small populations.

Constraint accounting (workbench step 10): `src/mapping/accounting.js` gives each constraint of either schema of a mapping (the Constraints tab's entries, `formalise` whole schema) a status with respect to the other schema: native, implied, lost (with a counterexample population) or unknown. Instead of unfolding χ syntactically it unfolds on populations: the smallest violation of χ is built from its counterexample formula (`negative.js`) with labelled nulls ⊥n (`buildViolations`), carried to the other side, closed under that side's constraints by a chase (`chase`: uniqueness merges labelled nulls, mandatory roles, inclusive/exclusive-or, subset and equality add facts; size-bounded), and carried back; still violated and valid there gives lost, else the chase constraints needed (each left out in turn) give native (one) or implied (several). A violation the rules don't carry is first completed by the side's own constraints, then by whole rule patterns (`complete`: kept by the rules if that removes it), then with rule constants (`withConstants`). Value and cardinality ranges and other kinds report unknown. The chase starts by closing the population under subtyping (a run builds only the types its rules name), and a violation that uniqueness alone rules out (`chase` with `tgds: false`) is decided without the facts mandatory roles would add, which keeps large schemas (AdventureWorks, about 2 min) tractable. `accountingSteps` yields per constraint; the Mappings tab's Accounting button runs it in slices (`AccountingReport.jsx`, result in `store.mappingAccounting`, not saved or undone), and `AccountingBadges` (MappingLayer.jsx) marks fact types with lost (red !) or unknown (grey ?) constraints on any diagram.

Broken-rule validation (workbench step 11): free edits of either schema leave rules naming deleted, moved or changed elements. `checkRule` reports them (a deleted fact type, column, table or variable type, a fact type whose arity changed, a role player or column type that no longer fits, lost key-safety), and `src/mapping/mappingIssues.js` collects them for the Validation panel: category Mapping Rules (one issue per rule problem, `elementKind: 'mappingRule'`, `mappingId`, `schemaIds` of both schemas, so it shows under either; a click opens the Mappings tab and the rule editor) and Mapping Coverage (entity and fact types that no rule of a mapping with rules names, as a warning on the element; value types, fully derived fact types and identifying fact types of a named entity are left out). The schema strip's mapping chip shows the number of rules with errors.

Derived entity types (workbench step 12, part 1): an entity type without supertypes can be derived or semi-derived through its reference scheme. Its rule's free variables are its reference values (`ref:0`…, `referenceParts` in `src/logic/derivationRule.js`, one per part of the reference mode or composite identifier), and each answer is an instance (the value, or the list of part cells), so the formula is ∀ā (∃e ident(e, ā) ↔ φ(ā)). `derivedPopulation.js` (`deriveByReference`) computes the population, and a fully derived one's identifying fact types take their tuples from it; `whyNotDerivableType` says why a type can't be derived (Inspector).

Fold (workbench step 12, part 2): `src/mapping/fold.js`. `planFold(state, mapping)` takes the fully derived types and fact types of one side (in dependency order) and unfolds each rule (∃, ∧, fact and type atoms, x ≈ 'c' only) through the mapping's atomic rules (`atomicOf`: a side that maps one fact type, or one entity type, between reference values): every variable becomes the slots of its reference values, identifying atoms join slots, and each other atom is replaced by the other side of its rule with frontier variables renamed to slots (`finishOther` then makes inner slots join variables, merges rows by primary key and entities by reference value, and drops rows another row implies). The derived element's own pattern over the frontier is the rule's other side. Fact types the rules used are removal candidates; `recoverable` drops their rules and runs the rest there and back on a generic population of the other side (`genericPopulation` in accounting.js: the dropped rules' other sides frozen with labelled nulls, chased). `foldChanges` checks the chosen removals together and adds mandatory roles and single-role uniqueness constraints that accounting finds kept (`suggestedConstraints`); `store.foldMapping` applies it as one undo step with a report in the import log. The Mappings tab's Fold… button opens `FoldDialog.jsx` (`store.foldDialog`).

Generating tables (workbench step 13): `src/relational/rmap.js` maps an ORM2 schema to a relational one the way Halpin's Rmap does. `planRelational` gives each entity type the columns of its reference scheme (natural key), absorbs a fact type with a simple uniqueness constraint on an entity's role into that entity's table (of a 1:1, the mandatory side), makes unaries boolean columns, gives other fact types (and objectified ones, keyed by their uniqueness constraint) tables of their own, and gives a subtype a table keyed by its supertype's key; an entity type gets a table when something is absorbed into it, it is independent, a sub/supertype, or plays no other role (the log notes the others). Surrogates follow decision Q4 (never / composite identifiers / always, per-type overrides): an identity column, natural key kept UNIQUE NOT NULL. Value ranges (type and role) become CHECKs. `generateRelational` writes the DDL (`planDdl`) and reads it back with `importPostgresDdl`, so the schema is exactly what that DDL gives, and builds one mapping rule per table row, absorbed fact type and fact table (joining over surrogates; an objectified type's row also names its fact). Objectified fact types without an identifier of their own are identified through their implied links in mappings (`sideContext` adds `<fid>_il_<i>` pseudo-facts, `keysOf` and `schemeOf` use them, `buildSide` adds the nesting fact's tuple). The dialog `GenerateRelationalDialog.jsx` (schema strip's + menu, `store.generateRelationalDialog`) previews the tables; `store.generateRelationalFromOrm` adds schema, diagram and mapping as one undo step and carries the population over by running the mapping.

Formula constraints (formula plan, step 1): a constraint with `constraintType: 'formula'` holds a closed formula of the logic as `rule`, in the rule-tree format of derivation rules (`src/logic/formulaConstraint.js`; no role sequences, optional `name` and `deontic`). The Formula tool (Advanced section of external constraints) places one and opens the rule editor in its formula mode (`openRuleEditor({ formulaId })`); `checkFormulaConstraint` gives the validation messages, `formulaConstraintEntry` the Constraints tab entry (verbalised and formalised like the others), `formulaConstraintPopulationIssues` (derivedPopulation.js, `closedFormula` on the evaluator) the population check with counterexamples, and accounting checks it through those issues. On the canvas it is a white φ circle, a pill when it shows a name, as for external frequency (`FormulaBadge` in ConstraintNodes.jsx; tool icon `FormulaConstraintIcon`) with dotted links to the fact types and object types its formula names (`formulaElements`).

CHECK constraints (formula plan, step 2): a CHECK of an imported DDL script is first split into its conjuncts (`splitCheck`): a comparison of two columns (with any `c IS NULL` alternatives for those columns) becomes a value comparison constraint over their value roles (named like the CHECK; exported back as `CHECK (a op b)` by `relationalModel`; value types of the same datatype kind may be compared), and a list or range of one column's values a value range. What is left becomes a formula constraint of its table (`src/relational/checkFormula.js`: `parseCheck` reads comparisons, IN, BETWEEN, LIKE/ILIKE, regular expressions, IS [NOT] NULL, arithmetic, ANY(ARRAY[…]) and a few functions; `checkToFormula` gives ∀t N(φ), with N "not false" and U "not true" so SQL's NULL semantics are kept, and drops `c IS NULL` disjuncts that a sibling comparison on c already covers). Unsupported conditions (NOW(), subqueries, CASE…) are left out with a warning. Unnamed CHECKs get PostgreSQL's name `table_column_check`. The constraint keeps `sqlCheck { text, columns: {name: factId}, rule }`; `sqlCheckOf` gives it back for the export (`relationalModel` table `checks`, written as `CONSTRAINT name CHECK (…)`, renamed columns renamed in the text) as long as the formula is unchanged; otherwise the export writes it from its formula (step 4).

Carrying constraints across a mapping (formula plan, step 3): `src/mapping/translate.js` writes a constraint that accounting reports lost over the other schema. `translateEntry` goes through the mapping's atomic rules as Fold does (`atomicRules`, `keyLeaves`, `schemeParts` from fold.js; a subtype may play its supertype's identifying role): each variable becomes the slots of its reference values, guarded by the other side of its entity type's rule unless a fact atom of the antecedent already says its type, each fact atom becomes the other side of its rule (opt inlined, not as ¬∃, constants as ≈), identifying facts become equalities, and `simplify` drops ≈-equal variables. `proposeTranslation` adds the result as a formula constraint to a copy of the state and runs accounting for that one key (`onlyKeys`), so the proposal says whether it keeps the constraint. The accounting report's translate link shows it (sentence, formula, check) with an Add button (`store.addCarriedConstraint`: drawn right of the fact types it names, one undo step). `asValueComparison` recognises ∀x̄ (φ → x op y) as a value comparison constraint with φ as its join query (a formula query); such a translation is added as one, and the Inspector offers "Turn into value comparison" for formula constraints of that shape (`store.formulaToValueComparison`). Accounting counts formula and value comparison violations of the other side as ruling a violation out, and evaluates formula constraints with all of the side's constraints (preferred identifiers give the tuples of identifying facts).

Constraints as SQL (formula plan, step 4): `src/relational/formulaSql.js` writes a constraint of a relational schema that has no table form (`relationalModel`'s `unwritten`: formula constraints not read from a CHECK, inclusive-or, exclusion, value comparisons across tables, …) from its formalised formula (`constraintEntries`). `formulaToSql` gives a CHECK when the formula is ∀t φ about one row t that reads only that row (a column read as v is its value when not NULL: ∀v (c(t, v) → p) is `c IS NULL OR p`, NOT NULL columns need no test), else a query that returns the violations (∀x̄ (φ → ψ): the x̄ with φ and not ψ; quantifiers become EXISTS over the tables their row variables range over, ∃ in an antecedent is pulled out, counts are COUNT(DISTINCT …), aggregates subqueries). Conditions are always true or false, never SQL's unknown. `exportPostgresDdl` adds the CHECKs to their tables and writes the queries as comments after the foreign keys; the Relational Profile validation says which constraints are only written as violation queries (not enforced) and why others are not written. Quoting is in `sqlNames.js`.

Equivalence summary (after formula plan step 4): `src/mapping/equivalence.js` gives one verdict per mapping (`equivalent`, `undecided` or `not`) from four checks: information of each side comes back after a run there and back (per rule, on its pattern's generic population; per entity type that may stand alone, `genericInstance` in accounting.js: tables always, ORM2 types only when independent or playing no other role; plus `uncoveredElements`), and the constraints of each side are kept in the other (constraint accounting). Kept constraints count as graphical unless a formula constraint of the other side is among their keepers; lost ones say whether their translation is a value comparison or a formula constraint (`translateEntry`, `asValueComparison`). Deontic constraints are left out. The Mappings tab's Equivalence button runs it in slices (`EquivalenceReport.jsx`, `store.mappingEquivalence`, not saved; stale once the elements or the mapping change) and also fills `store.mappingAccounting`, so the accounting report below it has the details.

File › Open also accepts NORMA `.orm` files: `src/import/norma.js` (`importNorma`) turns the XML into a FreeFBM model, which opens as a new unsaved model with an import log (`ImportLogPanel.jsx`); `src/import/openModelFile.js` routes the file. NORMA role paths (derivation rules of fact types and subtypes, hand-drawn join paths) become rule-tree formulas via `src/import/normaPaths.js`; positive linear self-recursion in a fully derived fact type's rule is rewritten as a TC* closure (`closeLinearRecursion`); outer joins and calculated values are not translated yet. Semi-derived rules may use themselves positively (least fixpoint over the stored population, `derivedPopulation.js`).

### Styling

`src/index.css` defines CSS custom properties for the entire design system (parchment/navy palette, ORM2 element colours, fonts). Components use these variables directly — no CSS-in-JS or utility framework.

## Architecture

This is an **Electron desktop application** for editing ORM2 (Object-Role Modeling 2) conceptual diagrams. The UI renders entirely in SVG on a pannable/zoomable canvas.

### Process split

- **Electron main** (`electron/main.cjs`) — window lifecycle, native menus, file dialogs (`.ffbm` JSON files; `.orm2`/`.json` still open; NORMA `.orm` is imported)
- **Preload** (`electron/preload.cjs`) — exposes `window.electronAPI` (openFile, saveFile, onMenuEvent) via context bridge
- **Renderer** — React 18 SPA served by Vite; communicates with main only through `window.electronAPI`

### State management

All application state lives in a single **Zustand store** (`src/store/ormStore.js`). This includes:
- ORM2 element data: `objectTypes`, `facts`, `subtypes`, `constraints`
- Interaction state: `selectedTool`, `selectedId`, `linkDraft` (multi-step operations), `pan`, `zoom`
- Undo/redo stacks: JSON snapshots, max 60 history entries (managed by `src/hooks/useUndoRedo.js`)

### ORM2 data model

| Element | Shape | Key fields |
|---|---|---|
| ObjectType | rect (entity) or ellipse (value) | `name`, `isValueType`, `x`, `y` |
| FactType | row of role boxes | `roles[]` (each has `objectTypeId`, uniqueness constraints) |
| Subtype | arrow between ObjectTypes | `superTypeId`, `subTypeId` |
| Constraint | graphical badge | `type` (Exclusion/Equality/Subset/Ring/Frequency), `roleGroups[]` |
| Group | none (colours its members) | `name`, `colors{outline,fill,text,graphics,floating,constraint,deontic,connector}` (NORMA colour roles), `priority`, `members[]` (element, role or note ids); see `src/utils/groups.js` |
| Schema | none (schema strip above the diagram tabs) | `name`, `profile` (`orm2` or `relational`); elements and diagrams carry `schemaId`, the active schema is the active diagram's; panels use `scopeToSchema`/`useScopedStore`. A relational schema is encoding B (table = entity type, column = binary fact type to a value type, see docs/logic/schema-mappings.tex), checked by the Relational Profile validation category, with PostgreSQL datatypes |
| Mapping | none (Mappings tab in the bottom panel) | `name`, `sourceSchemaId`, `targetSchemaId`, `rules[]` of `{name, source, target}`; each side is a pattern in the rule-tree format (∃, ∧, fact, type, `x ≈ $y`/`x ≈ 'c'` as vcmp, table row `rel`, optional `opt` [$y], `not`); see `src/mapping/mapping.js` and docs/logic/schema-mappings.tex |
| PropertyDefinition | none (values in each element's `properties`) | `name`, `category`, `type` (string/number/boolean/date/enum), `options`, `default`, `appliesTo[]`; see `src/utils/customProperties.js` |

Roles connect FactTypes to ObjectTypes; `RoleConnectors.jsx` draws the SVG lines.

### Tool modes

The active `selectedTool` in the store determines how canvas clicks are interpreted: `select`, `addEntity`, `addValue`, `addFact`, `assignRole`, `addSubtype`, `addConstraint`.

### File handling, Edit menu and Delete

`src/utils/fileActions.js` holds New, Open and Save for the toolbar and the menu: Save writes to the open `.ffbm` file without asking (`dialog:saveFile` with `path`), a new model, a NORMA import or a legacy `.orm2`/`.json` file asks for a path, Save As always asks, and Open and New ask before dropping unsaved changes. `src/hooks/useDocumentState.js` keeps the window title (file name, • while dirty, also shown in the toolbar after its buttons; on macOS the represented file and edited dot via `window:document`) and refuses to unload while dirty; `electron/main.cjs` (`guardUnsaved`) then asks Save… / Don't Save / Cancel on close, quit and (dev only) View › Reload, and Save asks the page to save (`app:saveThenClose`) and close (`window:closeNow`). The Edit menu sends `menu:undo` … `menu:selectAll` to the page, which runs the model's actions or, in a text field, passes them back as text editing (`window:nativeEdit`); accelerators are display-only on Windows and Linux (`registerAccelerator: false`). Delete rule (Jan, 2026-11-09; `src/utils/deleteSelection.js`): Delete/Backspace and Edit › Remove from Diagram take object types, fact types, external constraints and subtype links off the active diagram (on an ERD whole tables), delete notes, and remove internal constraints (bars, dots, frequencies, ranges) from their fact type; an element left on no diagram is named in the status bar (`store.orphanNotice`) with a link to Delete from Schema…. Deleting from the schema is only Delete from Schema… (Edit menu, context menus, Inspector, schema browser ×), which opens `DeleteFromSchemaDialog.jsx` (`store.deleteFromSchemaDialog = { ids }`, `deletionSummary` lists what goes with it) and deletes as one undo step; not offered on read-only relational schemas.

### File format

Files are saved as `.ffbm` (JSON; the legacy `.orm2` and `.json` extensions still open). The store's `exportModel()` / `importModel()` functions serialise/deserialise all four element collections.

File › Import SQL DDL (PostgreSQL, Oracle or SQL Server)… reads a `.sql` script into a new relational schema of the open file (`src/relational/ddlParse.js` parses CREATE TABLE / ALTER TABLE ADD CONSTRAINT and ADD/DROP/RENAME/ALTER COLUMN / enums / domains / unique indexes; `ddlImport.js` builds encoding B with one diagram, as one undo step via `store.historyBatch`); File › Export PostgreSQL DDL… writes the active relational schema (`ddlExport.js`).

A diagram of a relational schema is drawn as an ERD (crow's foot, read-only) while the schema shows its relational face (`isErdDiagram`, `src/relational/face.js`; mapping diagrams always ORM2); `src/components/ErdView.jsx` draws the tables that `src/relational/relationalModel.js` reads from encoding B (shared with the DDL export), with box positions in `diagram.erdPositions` (Auto layout clears them; `fitToContent` fits an ERD's boxes at most 100% and Reset View shows it at 100%, both with the top-left table 40 px from the canvas corner, `erdBounds` in diagramSlice.js; Generate, Guess and the DDL import fit the new diagram); `src/relational/erdRouting.js` places tables in columns by FK depth (then barycentre sweeps for fewer crossings and heights near the tables each is joined to, `spread1D`). FK lines are drawn by default as in DBeaver (our own code, ideas only): `src/relational/erdDirect.js` attaches each line at its column's row (`assignRowPorts`, ends on one side ordered by the direction of their other end), gives both ends a straight stub for the crow's foot, and routes a shortest path between the stubs over a visibility graph of enlarged box corners (`routeDirect`: extra cost for crossing earlier lines, crossing or grazing another line's crow's foot, sharing a corner, or turning back at a stub); lines bending at one corner are moved apart (`separateCorners`). The Diagonal | Right-angled switch next to Auto layout (`diagram.erdLines`, `store.setErdLines`) picks the older right-angled router (`routeLines`/`assignPorts` in erdRouting.js). Clicking a line selects the FK's subset constraint and highlights its columns. Box sizes and positions live in `src/relational/erdBoxes.js` (`erdLayout`, `mappingErdBoxes`, `erdPartsOfDiagram`); `erdTargetOf` finds where an element (table, column, value type, key, FK, CHECK) is drawn, which `centerOnElement` uses (so a click on a validation message goes to the table or column row, not the ORM2 occurrence) and which ErdView uses for validation badges on tables (issues top right, sample-row violations top left, popup in `BadgePopup.jsx`, shared with Canvas). Column types the PostgreSQL profile doesn't know (extensions, CREATE TYPE) are kept as datatype `user-defined` with their SQL text. Assertion nodes (the Assertions n switch right of Diagonal | Right-angled, `diagram.erdAssertions`, `store.setErdAssertions`; shown only when the schema has assertions): `src/components/ErdAssertions.jsx` draws each assertion (relationalView kind `assertion`) whose tables are all on the diagram as an ORM2-style constraint circle (a pill with its name), with the glyph of its kind, and links it to the table boxes: solid to a table it constrains, dashed with an arrow to one it only references. `src/relational/erdAssertions.js` reads both from the formula, not from where the assertion came from: the kind is `asGraphical`'s shape (⊆ = ⊗ ∨ ⊕ u, frequency range, value comparison), else the constraint's own graphical type, else ↺ for a transitive closure, Σ for an aggregate, else φ (`assertionKind`); a table is constrained when its atoms occur negatively (∀, antecedent, ¬, counted with an upper bound: adding rows can break it) and referenced when only positively (`assertionTables`). Positions are free spots near the tables (`placeAssertions`), or `diagram.erdAssertionPositions` once one is dragged (`setErdAssertionPositions`; Auto layout clears them). Hovering or selecting a node highlights its tables and the columns it reads. The relational Inspector gives an assertion's kind, tables and origin: `addCarriedConstraint`'s `from` is kept as `carriedFrom { mappingId, schemaId, text }` (Accounting report, carry panel, Generate's carryLost, transformations).

Mappings (workbench step 7): `src/mapping/mapping.js` holds the pattern format, its flat form (`treeToSide`), the expansion of table-row atoms into encoding B (`expandSide`), and `checkRule` (well-formedness, types, the P2 binding rules for frontier variables, key-safety via `determined`); the Mappings tab (`MappingsTab.jsx`) lists mappings and their rules as formulas with check messages, and rules are edited live in the floating `MappingRuleEditor.jsx` (`store.mappingRuleEditor`), a pattern mode of the derivation rule editor's click-to-select tree editing (it reuses VarSelect/ConstInput from `DerivationRuleEditor.jsx`). Mappings are saved in the file (`schema.mappings`) and are part of undo.

Basic and Advanced mode (the switch at the top of the tool panel, `store.advancedMode`, kept in localStorage `freefbm.advancedMode`): in Basic mode mappings come only from Generate, Guess and Fold, the Mappings tab shows rules read-only (no Add mapping, + Rule, Edit or reordering; a rule with errors offers Drop rule), and `openMappingRuleEditor` scrolls to and highlights the rule (`store.mappingRuleFocus`) instead of opening the editor. Advanced mode keeps hand editing.

Mapping diagrams (workbench step 7b): a diagram with `mappingId` draws that mapping; it belongs to the mapping's source schema (`schemaId`, where new elements go) but may hold occurrences of both schemas (`activeScopeIdsOf`/`scopeToSchema` then scope panels to both). The schema strip lists mappings as chips and the Mappings tab has a Diagram button; both call `store.openMappingDiagram`, which makes the first diagram with the elements the rules name (`addMappingRuleElements`: home positions from each schema's own diagrams, target side to the right). `src/components/MappingLayer.jsx` tints elements by side (MappingTints) and draws each rule as a node linked to its elements (MappingRules; hover highlights via `store.ruleHighlight`, click opens the rule editor, drag stores `diagram.mappingRulePositions`). Mapping diagrams are drawn in ORM2, with a relational side in its relational face as ERD tables (RM step 7). A mapping diagram draws a subset of the rules (`diagram.mappingRuleIds`; a rule on the diagram brings every element it names; a new tab next to a mapping diagram starts with none; older files get the rules whose elements they show, `withExplicitRuleIds` in src/mapping/diagramRules.js; `diagramRuleIds` in storeHelpers.js); on a mapping diagram the schema browser lists the mapping's rules instead of elements (`MappingRuleBrowser.jsx`: rules on this diagram, other rules, rules on no diagram as orphans, filter by name or formula; a click centres on the rule's node and opens it): + adds a rule with the elements it names (`store.showMappingRules` → `placeMappingRule`: new elements close together beside the rule's node, source left and target right, ERD tables pinned in `erdPositions`, by `compactRulePlacement`), − takes it off with the elements no remaining rule needs (`hideMappingRules`), and the row menu has New Diagram with This Rule (`newMappingDiagram`). Suggest diagrams (`SuggestDiagramsDialog.jsx`, the Mappings tab's Suggest diagrams… button, `store.suggestDiagramsDialog = { mappingId }`) splits a mapping's rules (all, or those on no diagram) into groups to review: `src/mapping/ruleClusters.js` (`clusterRules`) gives each rule the elements a diagram shows for it on either side (`ruleInfo`, from `ruleWantedElements`), clusters in two levels by Louvain-style local moves (level 1: constant Potts model on Jaccard similarity weighted by rarity, the rules about one type or table; level 2: modularity over plain Jaccard without value types, joining those groups), splits groups drawing more than a cap of shapes (ERD sides count tables only; default 50, localStorage `freefbm.suggestDiagrams.cap`) and merges while modularity rises under the cap, small groups joining their best neighbour; repeated runs with other seeds and resolutions mark groups that vary and rules another group holds more often (`unsure`). The dialog lets the user rename, move rules, merge and leave out groups; `store.newMappingDiagrams(mappingId, groups, { layout })` makes one mapping diagram per group as one undo step, each laid out by `layoutMappingDiagram`. Rule nodes can be selected (shift- or Cmd-click, or the canvas rubber band, which picks nodes whose centre is in it; `store.selectedRuleIds`, session only, cleared with the selection and on switching diagrams); dragging a selected node moves them all (`setMappingRulePositions`), and the right-click menu (also in the multi-selection menu) has Move / Copy n Rules to New Diagram (`store.rulesToNewDiagram(diagramId, ruleIds, { move, layout })`: a diagram "<diagram> part n" made by `newMappingDiagrams` and auto laid out; move first takes the rules off with `hideMappingRules`; one undo step) and Remove n Rules from Diagram. Mapping diagram auto layout (`src/layout/mappingLayout.js`, the Auto layout link beside Add rule elements): each ORM2 side is laid out by the ORM2 auto layout on its own (`layoutOrmDiagram` with `satOrder`, so an entity type's attributes follow the column order of the table they map to), the anchor side (the larger ORM2 side, else the source) stays, an ERD side's tables go in a column (two when much taller) in the order of where their rules' elements are on the anchor side (`spread1D`), an ORM2 non-anchor side is turned upside down when that puts related elements level (not with subtypes), and the rule nodes sit in a column between source (left) and target (right), each at the mean height of the fact types or columns it links (two staggered columns when crowded); an ERD side's hidden occurrences move to their tables. Below a mapping or view diagram the Mappings tab lists only that mapping and the rules on the diagram (`MappingsTab.jsx` scoped by `diagramRuleIds`, `ViewMappings` `only`; exchanges and other mappings hidden), with an All rules switch (localStorage `freefbm.mappings.allRules`).

Running mappings (workbench step 8): `src/mapping/runMapping.js` matches one side of each rule against its schema's population (`matchSide`, backtracking with fact indexes; opt binds $y to null, not filters) and builds the other side's population (`buildSide`: entity instances come from their reference schemes, ref mode or composite identifier, so the same key gives the same instance; identifying facts are not stored as tuples). `runMapping(state, mapping, 'forward'|'backward')` returns the built populations with per-rule match counts and a log; `withRunApplied` swaps them into the target schema (`store.applyMappingRun`, one undo step); `roundTrip` runs there and back and compares each type and fact population of the source (lost/gained, plus types and facts no rule reads). The Mappings tab has Run →, Run ← and Round trip buttons. Sample rows come from `INSERT … VALUES` statements and `COPY … FROM stdin` blocks (text or CSV, `extractCopies` takes them out before tokenizing; rows of a partition go to its table) in an imported DDL script (`ddlParse` `inserts`, `ddlImport.samplePopulation`: booleans as true/false, at most 20,000 rows shared fairly so small tables are read whole), or from a separate data script via File › Load Sample Rows from SQL… (`store.loadSampleRows`, replaces the active relational schema's population; e.g. pagila-data.sql).

Guessing an ORM2 schema (workbench step 9): `src/relational/guessOrm.js` reads a relational schema (`relationalModel`) back as ORM2 and writes the mapping to it. `analyseTables` classifies each table (entity, subtype when its primary key is a foreign key to another table's key, junction when all columns are in its foreign keys and its key and nothing references it, nokey) and finds surrogates (a one-column key with generated values: SERIAL, IDENTITY, a sequence or UUID default) and natural keys (UNIQUE, NOT NULL, not generated); `guessOrmSchema` builds entity types (singular Pascal-case names), reference modes or preferred external uniqueness constraints, attribute and foreign-key fact types (readings from column names), m:n fact types, and one mapping rule per entity type, attribute and foreign key, joining over a dropped surrogate in the source pattern. Step 5 of the stock-take: a boolean NOT NULL column (a flag) becomes a unary fact type (`flagReading`: "is active", "is salaried"; two rules, `col ≈ true` gives the fact, `col ≈ false` an entity without it); a table whose only column is its key, referenced and referencing nothing (kind `lookup`), becomes a value type whose instances are its rows (a rule with a type atom), and the columns referring to it play it (`p.fks` leaves such foreign keys out); a type column (named …type/kind/class/category/role, with a list of values declared or ≤ 8 distinct sample values, `discriminatorValues`) gives a fully derived subtype per value, and a nullable column filled only in sample rows of one value moves to that subtype (accounting does not yet see that the relational side allows it elsewhere). The dialog `GuessOrmDialog.jsx` (store `guessOrmDialog`, opened from the schema strip's + menu) lets the user keep or drop each surrogate; `store.guessOrmFromRelational` adds schema, diagram (rows by foreign-key depth) and mapping as one undo step. When a run builds a table whose surrogate nothing gives, `runMapping` invents it from another key (`⟨values⟩`, `altKeysOf`), and `roundTrip` compares such surrogates up to renaming (`surrogateRenaming`). The invented key is the same in every rule (`prepareRun` → `inventKeys`); `prepareRun`/`executeRun` split a run so it can be repeated cheaply on small populations.

Constraint accounting (workbench step 10): `src/mapping/accounting.js` gives each constraint of either schema of a mapping (the Constraints tab's entries, `formalise` whole schema) a status with respect to the other schema: native, implied, lost (with a counterexample population) or unknown. Instead of unfolding χ syntactically it unfolds on populations: the smallest violation of χ is built from its counterexample formula (`negative.js`) with labelled nulls ⊥n (`buildViolations`), carried to the other side, closed under that side's constraints by a chase (`chase`: uniqueness merges labelled nulls, mandatory roles, inclusive/exclusive-or, subset and equality add facts; size-bounded), and carried back; still violated and valid there gives lost, else the chase constraints needed (each left out in turn) give native (one) or implied (several). A violation the rules don't carry is first completed by the side's own constraints, then by whole rule patterns (`complete`: kept by the rules if that removes it), then with rule constants (`withConstants`). Cardinality ranges are checked by evaluating their formula (a matcher's `evaluate`); value ranges and other kinds without a violation shape report unknown. The chase also applies formula constraints, and subset/equality/inclusive-/exclusive-or constraints with formula queries, as TGDs from their formulas (`tgdsOf`: each conjunct ∀ȳ (L → R) with positive L and R, R built by `buildRight`; R a disjunction of positive parts is a choice point); a frequency counted above its upper bound is a break no added fact mends (`tooMany`). Violations may use objectified fact types identified through their implied links and TC atoms (a path of 1–3 steps). Disjunctions (inclusive-/exclusive-or over roles or subtypes, implicit participation with several roles) are choice points of the chase (`choices`/`points`); the other side's chase is run in every case (`chaseBranches`, at most 64), and a violation counts as ruled out only when it is in all of them. Before branching, a uniqueness-only chase that fails, or a break no added fact mends (exclusion, ring, value range, value comparison, an exclusive-or instance in two parts), rules it out at once; a constraint that asks for facts stops a case as soon as the violation is gone (`until`). The chase starts by closing the population under subtyping (a run builds only the types its rules name), and a violation that uniqueness alone rules out (`chase` with `tgds: false`) is decided without the facts mandatory roles would add, which keeps large schemas (AdventureWorks, about 2 min) tractable. `accountingSteps` yields per constraint; the Mappings tab's Accounting button runs it in slices (`AccountingReport.jsx`, result in `store.mappingAccounting`, not saved or undone), and `AccountingBadges` (MappingLayer.jsx) marks fact types with lost (red !) or unknown (grey ?) constraints on any diagram.

Broken-rule validation (workbench step 11): free edits of either schema leave rules naming deleted, moved or changed elements. `checkRule` reports them (a deleted fact type, column, table or variable type, a fact type whose arity changed, a role player or column type that no longer fits, lost key-safety), and `src/mapping/mappingIssues.js` collects them for the Validation panel: category Mapping Rules (one issue per rule problem, `elementKind: 'mappingRule'`, `mappingId`, `schemaIds` of both schemas, so it shows under either; a click opens the Mappings tab and the rule editor) and Mapping Coverage (entity and fact types that no rule of a mapping with rules names, as a warning on the element; value types, fully derived fact types and identifying fact types of a named entity are left out). The schema strip's mapping chip shows the number of rules with errors.

Derived entity types (workbench step 12, part 1): an entity type without supertypes can be derived or semi-derived through its reference scheme. Its rule's free variables are its reference values (`ref:0`…, `referenceParts` in `src/logic/derivationRule.js`, one per part of the reference mode or composite identifier), and each answer is an instance (the value, or the list of part cells), so the formula is ∀ā (∃e ident(e, ā) ↔ φ(ā)). `derivedPopulation.js` (`deriveByReference`) computes the population, and a fully derived one's identifying fact types take their tuples from it; `whyNotDerivableType` says why a type can't be derived (Inspector).

Fold (workbench step 12, part 2): `src/mapping/fold.js`. `planFold(state, mapping)` takes the fully derived types and fact types of one side (in dependency order) and unfolds each rule (∃, ∧, fact and type atoms, x ≈ 'c' only) through the mapping's atomic rules (`atomicOf`: a side that maps one fact type, or one entity type, between reference values): every variable becomes the slots of its reference values, identifying atoms join slots, and each other atom is replaced by the other side of its rule with frontier variables renamed to slots (`finishOther` then makes inner slots join variables, merges rows by primary key and entities by reference value, and drops rows another row implies). The derived element's own pattern over the frontier is the rule's other side. Fact types the rules used are removal candidates; `recoverable` drops their rules and runs the rest there and back on a generic population of the other side (`genericPopulation` in accounting.js: the dropped rules' other sides frozen with labelled nulls, chased). `foldChanges` checks the chosen removals together and adds mandatory roles and single-role uniqueness constraints that accounting finds kept (`suggestedConstraints`); `store.foldMapping` applies it as one undo step with a report in the import log. The Mappings tab's Fold… button opens `FoldDialog.jsx` (`store.foldDialog`). Semi-derived elements fold too, when a rule of the mapping already names them: the element becomes stored (stored and derived rows), and its rule's formula (`derivationEntry`/`factDerivationEntries` via `entriesOf`, `formulaToRule`) is kept as a constraint (`changes.constraints`, added by foldMapping with `addCarriedConstraint`): a subset constraint when `asGraphical` recognises one (or the same suggested foreign key), else a formula constraint; it is dropped when it reads a removed fact type. Accounting's chase applies semi-derivation rules as TGDs (`tgdsOf`). Transformations fold only the fully derived elements they make.

Generating tables (workbench step 13): `src/relational/rmap.js` maps an ORM2 schema to a relational one the way Halpin's Rmap does. `planRelational` gives each entity type the columns of its reference scheme (natural key), absorbs a fact type with a simple uniqueness constraint on an entity's role into that entity's table (of a 1:1, the mandatory side), makes unaries boolean columns, gives other fact types (and objectified ones, keyed by their uniqueness constraint) tables of their own, and gives a subtype a table keyed by its supertype's key; an entity type gets a table when something is absorbed into it, it is independent, a sub/supertype, or plays no other role (the log notes the others). Surrogates follow decision Q4 (never / composite identifiers / always, per-type overrides): an identity column, natural key kept UNIQUE NOT NULL. Value ranges (type and role) become CHECKs, and so do inclusive-or, exclusive-or, exclusion, equality and subset constraints whose roles are all on the entity side of fact types absorbed into one table (`constraintCheck`: a role is played when its columns are all filled in, a unary when its column is true; e.g. `CHECK (email IS NOT NULL OR phone IS NOT NULL)`). `generateRelational` writes the DDL (`planDdl`) and reads it back with `importPostgresDdl`, so the schema is exactly what that DDL gives, and builds one mapping rule per table row, absorbed fact type and fact table (joining over surrogates; an objectified type's row also names its fact). Objectified fact types without an identifier of their own are identified through their implied links in mappings (`sideContext` adds `<fid>_il_<i>` pseudo-facts, `keysOf` and `schemeOf` use them, `buildSide` adds the nesting fact's tuple). The dialog `GenerateRelationalDialog.jsx` (schema strip's + menu, `store.generateRelationalDialog`) previews the tables; `store.generateRelationalFromOrm` adds schema, diagram and mapping as one undo step, adds each ORM2 constraint the tables don't keep as its translation (option `assertions`, the dialog's "Keep every constraint" checkbox; `carryLost` in mappingSlice.js: constraint accounting, `proposeTranslation`, `addCarriedConstraint`; a CHECK, a graphical constraint over columns or an assertion), and carries the population over by running the mapping.

Carrying diagrams (Generate tables and Guess ORM2): when the schema the mapping is made from has two or more plain diagrams, the new schema gets a twin of each, named alike, after its diagram of everything (`src/mapping/carryDiagrams.js`, `store.carrySchemaDiagrams`, inside the action's undo batch; the dialogs' "Keep the n diagrams" checkbox, option `diagrams`). A rule belongs to a diagram when the diagram shows all of its core elements on that side (`ruleCore`: tables and non-identifying fact types; else type atoms; else the most specific ∃ variable entity types; else what its identifying facts identify); the twin shows what the diagram's rules name on the other side (`ruleWantedElements` plus ∃ variable types, then subtype links between shown types and the external constraints they allow), laid out by the ORM2 auto layout passed in as `layout` (ERD boxes by the ERD's own). A diagram all rules belong to (the import's Tables diagram) renames the diagram of everything instead.

Formula constraints (formula plan, step 1): a constraint with `constraintType: 'formula'` holds a closed formula of the logic as `rule`, in the rule-tree format of derivation rules (`src/logic/formulaConstraint.js`; no role sequences, optional `name` and `deontic`). The Formula tool (Advanced section of external constraints) places one and opens the rule editor in its formula mode (`openRuleEditor({ formulaId })`); `checkFormulaConstraint` gives the validation messages, `formulaConstraintEntry` the Constraints tab entry (verbalised and formalised like the others), `formulaConstraintPopulationIssues` (derivedPopulation.js, `closedFormula` on the evaluator) the population check with counterexamples, and accounting checks it through those issues. On the canvas it is a white φ circle, a pill when it shows a name, as for external frequency (`FormulaBadge` in ConstraintNodes.jsx; tool icon `FormulaConstraintIcon`) with dotted links to the fact types and object types its formula names (`formulaElements`).

CHECK constraints (formula plan, step 2): a CHECK of an imported DDL script is first split into its conjuncts (`splitCheck`): a comparison of two columns (with any `c IS NULL` alternatives for those columns) becomes a value comparison constraint over their value roles (named like the CHECK; exported back as `CHECK (a op b)` by `relationalModel`; value types of the same datatype kind may be compared), and a list or range of one column's values a value range. What is left becomes a formula constraint of its table (`src/relational/checkFormula.js`: `parseCheck` reads comparisons, IN, BETWEEN, LIKE/ILIKE, regular expressions, IS [NOT] NULL, IS [NOT] TRUE/FALSE (never unknown, so a NULL does not pass `c IS TRUE`), arithmetic, ANY(ARRAY[…]) and a few functions; `checkToFormula` gives ∀t N(φ), with N "not false" and U "not true" so SQL's NULL semantics are kept, and drops `c IS NULL` disjuncts that a sibling comparison on c already covers). Unsupported conditions (NOW(), CASE…) are left out with a warning. Unnamed CHECKs get PostgreSQL's name `table_column_check`. The constraint keeps `sqlCheck { text, columns: {name: factId}, rule }`; `sqlCheckOf` gives it back for the export (`relationalModel` table `checks`, written as `CONSTRAINT name CHECK (…)`, renamed columns renamed in the text) as long as the formula is unchanged; otherwise the export writes it from its formula (step 4).

Assertions read back from SQL (assertion nodes, step 2): `parseDdl` also returns `assertions` (`CREATE ASSERTION name CHECK (…)`) and `functions` (CREATE FUNCTION name → `{ params, body, language, returns }`). The CHECK parser reads subqueries: `EXISTS (SELECT …)`, `x IN (SELECT …)`, a scalar `(SELECT …)` and aggregates (`select()` gives FROM items with aliases and folds inner JOIN … ON into WHERE; LEFT/RIGHT joins, USING, GROUP BY are not read), `$n` parameters, and calls of the script's own LANGUAGE sql functions, inlined (`RETURN e`, `SELECT cond`, or `SELECT agg … FROM …` as a scalar subquery; arguments are marked `argOf` their call so they resolve in the caller's scope). `translate` (shared by `checkToFormula` and `assertionToFormula`) gives each subquery row a variable of its table's entity type (`tables(name, schema)` resolves names) and uses four modes, N/U plus T (true, ¬U) and F (false, ¬N): EXISTS is ∃r̄ T(where) (U/F: ∀r̄ U(where)), IN is ∃r̄ (T(where) ∧ mode(x = e)), COUNT(*) compared with a number a counting quantifier ∃^{op n}, and so is COUNT(DISTINCT …) as the exports write counts: of a row's key columns (also `COUNT(DISTINCT (a, b))` and `COUNT(*) FROM (SELECT DISTINCT a, b …) AS d`) a count of those rows, of one other column a count of its values (`tableFor` gives each table's `key`); when other tables are read, `tidy` turns ¬∃ into ∀ → and `mergeEqual` drops ≈-equal variables. A CHECK that reads other tables (subquery or function) becomes a formula constraint without `sqlCheck`, kept as `sqlSource { kind: 'check', table, text }` (so it is an assertion, exported with constraint triggers); each CREATE ASSERTION becomes one with `sqlSource { kind: 'assertion', text }` (SUM/AVG and other unsupported parts leave it out with a warning; triggers and PL/pgSQL bodies are not read). The relational Inspector gives sqlSource as the origin, and `assertionKind` falls back to `looseShape` (⊆ for a positive implication or a positive body of several atoms, ⊗ for L → ¬positive or ¬(positive conjunction)) before φ.

Carrying constraints across a mapping (formula plan, step 3): `src/mapping/translate.js` writes a constraint that accounting reports lost over the other schema. `translateEntry` goes through the mapping's atomic rules as Fold does (`atomicRules`, `keyLeaves`, `schemeParts` from fold.js; a subtype may play its supertype's identifying role): each variable becomes the slots of its reference values, guarded by the other side of its entity type's rule unless a fact atom of the antecedent already says its type, each fact atom becomes the other side of its rule (opt inlined, not as ¬∃, constants as ≈), identifying facts become equalities, a transitive closure over entities with one reference value each becomes the closure of its body's translation over those values (so acyclic and strongly intransitive rings carry over), and `simplify` drops ≈-equal variables and reads a row found again through a unique column as the same row (`unique`; a guard on the row's mandatory key goes, `mandatory`), so a carried constraint about one row is written as a CHECK. `proposeTranslation` adds the result as a formula constraint to a copy of the state and runs accounting for that one key (`onlyKeys`), so the proposal says whether it keeps the constraint. The accounting report's translate link shows it (sentence, formula, check) with an Add button (`store.addCarriedConstraint`: drawn right of the fact types it names, one undo step). `src/mapping/recognise.js` (`asGraphical`) recognises the shapes of graphical constraints with join paths among formulas: value comparison ∀x̄ (φ → x op y), subset ∀x̄ (L → R), equality (L ↔ R, under a guard), exclusion, frequency/uniqueness ∀x̄ (G ∧ ∃t ψ → ∃^{…} t ψ) and inclusive-/exclusive-or (about one variable, or about the instance z of a guard ∃z F(z, y)), with formula queries as join paths. `proposeTranslation` tries the recognised constraint too (also when the formula's own check is undecided) and keeps it when accounting says it keeps the constraint; such a translation is added as that graphical constraint (`graphicalFields`, `GRAPHICAL_NAME`), and the Inspector offers "Turn into …" for formula constraints of those shapes (`store.formulaToGraphical`). Accounting counts formula and value comparison violations of the other side as ruling a violation out, and evaluates formula constraints with all of the side's constraints (preferred identifiers give the tuples of identifying facts).

Constraints as SQL (formula plan, step 4): `src/relational/formulaSql.js` writes a constraint of a relational schema that has no table form (`relationalModel`'s `unwritten`: formula constraints not read from a CHECK, inclusive-or, exclusion, value comparisons across tables, …) from its formalised formula (`constraintEntries`). `formulaToSql` gives a CHECK when the formula is ∀t φ about one row t that reads only that row (a column read as v is its value when not NULL: ∀v (c(t, v) → p) is `c IS NULL OR p`, NOT NULL columns need no test), else a query that returns the violations (∀x̄ (φ → ψ): the x̄ with φ and not ψ; quantifiers become EXISTS over the tables their row variables range over, ∃ in an antecedent is pulled out, counts are COUNT(DISTINCT …), aggregates subqueries, a transitive closure [TC_{v,w} φ](s, t) a `WITH RECURSIVE` query of what s reaches, started at s, with UNION so cycles stop; TC* also holds when s = t). Conditions are always true or false, never SQL's unknown. `exportPostgresDdl` adds the CHECKs to their tables and writes the queries as comments after the foreign keys. A relational schema is a relational schema in general, not a PostgreSQL one: any constraint over its tables is fine (one with no table form is an assertion), so the Relational Profile validation reports only what breaks encoding B, and what PostgreSQL can't enforce (assertions written as violation queries, constraints not written, keys of views) is reported at File › Export PostgreSQL DDL… by `DdlExportDialog.jsx` (`store.ddlExportDialog`, from `exportPostgresDdl`'s `plan` and `warnings`) before saving. Quoting is in `sqlNames.js`.

Enforcing constraints per SQL DBMS (stage 1, PostgreSQL; plan in the Claude doc "Enforcing constraints per SQL DBMS"): `src/relational/enforcement.js` lists the targets (`SQL_TARGETS`: PostgreSQL, Oracle and SQL Server ready; MySQL, SQLite later) and plans each constraint of a relational schema (`planEnforcement(state, schemaId, settings)`): table form (NOT NULL, keys, foreign keys, CHECKs, from relationalView), check (a constraint with no table form about one row, written as a CHECK by formulaSql), foreignKey (an assertion that is a foreign key in disguise, `asForeignKey` in `src/relational/foreignKeyRewrite.js`: ∀x̄ (L → ∃r T(r, x̄)) with L one row of S plus NOT NULL columns read into unused variables and guard rows that S's foreign keys give, into columns holding a key of T, with an added UNIQUE when they are more than a key; one already declared is reported as the same), trigger, audit (commented violation query) or none, each with status enforced / partly / not. A foreign key to columns that are not a key (SQL refuses it) is planned as an assertion (`fk:` rmId). The schema keeps its SQL settings (`schema.sql = { target, assertions: 'triggers'|'audit', overrides: { rmId: 'trigger'|'audit' } }`, `sqlSettings`, `store.setSchemaSql`, saved in the file; deontic constraints are always audit queries). `exportPostgresDdl` follows the plan (options `assertions`, `overrides` override the schema's) and returns it as `plan`; File › Export PostgreSQL DDL… always opens `DdlExportDialog.jsx` (target, the trigger-or-audit choice and a per-assertion one, counts, assertions, CHECK rewrites, the table form), and the relational Inspector says how an assertion is enforced (`EnforcedAs`).

Oracle (stage 2): SQL text is written per dialect (`withDialect(dialect, fn)`/`sqlDialect()` in sqlNames.js; Oracle quoting and reserved words; relationalView caches PostgreSQL text, so compute it before switching). formulaSql's Oracle branch writes DECODE for IS DISTINCT FROM, TO_CHAR/TRUNC/REGEXP_LIKE/SUBSTR/INSTR, counts of several values as COUNT(*) over SELECT DISTINCT, and a transitive closure as a recursive WITH with a CYCLE clause that starts at every row and keeps its start column (Oracle cannot correlate a WITH inside a subquery; a closure with outside parameters is refused); viewSql uses FETCH FIRST and CAST(NULL AS …); a CHECK read from the script (`sqlCheck`) is rewritten from its formula. `src/relational/oracleAssertions.js` (`oracleAssertion`) says whether a violation query can be a CREATE ASSERTION (NOT EXISTS, comma joins, no aggregates, WITH, ANSI joins, nesting ≤ 3) and whether Oracle will likely accept its joins (all along NOT NULL foreign keys); the planner's technique `assertion` (DEFERRABLE INITIALLY DEFERRED when a table occurs positively, `assertionTables`' `positive`). `src/relational/oracleDdl.js` (`exportOracleDdl`, `oracleType` maps the column types) writes each assertion as a PL/SQL block that tries CREATE ASSERTION and, when Oracle refuses it, creates statement triggers (AFTER INSERT OR UPDATE OR DELETE, RAISE_APPLICATION_ERROR -20001) or leaves it as an audit query, printing the error stack; `src/relational/sqlExport.js` (`exportSqlDdl`) picks the writer by target. The menu item is File › Export SQL DDL….

Oracle import: `parseDdl(sql, { dialect })` reads Oracle scripts too (`detectDialect`: VARCHAR2, NUMBER(…), CLOB, BINARY_*, ENABLE, lines holding only /). In Oracle mode the tokenizer folds upper-case quoted names ("EMPLOYEES") to the unquoted lower-case name, reads q'[…]' strings, and ends PL/SQL units (triggers, procedures, packages, types, anonymous blocks) at a / line; SQL*Plus command lines (REM, PROMPT, SET …) are dropped. It reads storage clauses, USING INDEX, ENABLE/NOVALIDATE (skipped), ALTER TABLE ADD (…) and MODIFY, DBMS_METADATA's unique indexes behind keys (deduplicated), INSERTs inside anonymous blocks and INSERT ALL, TO_DATE/TO_TIMESTAMP/DATE '…' literals (`oracleDate` reads the format model), REGEXP_LIKE in CHECKs (as ~), a BEFORE INSERT trigger filling :NEW.col from a sequence (the column is a surrogate), and FreeFBM's own Oracle export back: EXECUTE IMMEDIATE 'CREATE ASSERTION …' and statement triggers that raise on WHERE EXISTS (violation query) become assertions. `oracleAssignment` (ddlImport.js) gives each Oracle type the nearest PostgreSQL type (NUMBER(p) smallint/integer/bigint by precision, DATE timestamp(0), VARCHAR2 character varying, CLOB text, BLOB/RAW bytea) and keeps the Oracle type in the assignment's `oracle` field, which `oracleType` writes back; the import log notes DATE columns and that Oracle's empty string is NULL.

SQL Server (stage 3): one type system, the profile "SQL types" (id `postgresql`; types only PostgreSQL has are marked `ext: 'postgresql'`, "(PostgreSQL only)" in the Inspector); an assignment read from another DBMS keeps its own type text in `sqlTypes: { oracle, sqlserver }` (`nativeType`/`nativeTypes` in sqlNames.js; the older `oracle` field is still read; editing a parameter drops them), which that DBMS's export writes back. T-SQL text (`sqlDialect() === 'sqlserver'`): [bracket] quoting (TSQL_RESERVED, names compared without case), no TRUE/FALSE (`tsqlBooleans` writes (1 = 1)/(1 = 0)), BIT for booleans, TOP 1 and OUTER APPLY in views, CASE for iff, CONCAT/LEN/SUBSTRING/CHARINDEX/DATEFROMPARTS/DATEPART (`tsqlTerm`), a regular expression only as LIKE with [classes] (`regexToLike`; SQL Server has them only from 2025), and a transitive closure as a recursive CTE hoisted to the top of the query (a CTE can't sit inside EXISTS; `finish` returns `with` and `body`), with a path column against cycles and OPTION (MAXRECURSION 0). `src/relational/mssqlDdl.js` (`exportSqlServerDdl`, `sqlServerType`) writes GO batches: tables (key columns of MAX types shortened to NVARCHAR(450)/VARBINARY(900), UNIQUE over nullable columns as a filtered unique index WHERE … IS NOT NULL, since SQL Server's UNIQUE allows one NULL), foreign keys, views, and each assertion as an AFTER INSERT, UPDATE, DELETE trigger per table that THROWs 50001 when its violation query returns rows (checked after each statement: SQL Server has no deferred triggers, so the planner marks assertions that ask for rows `mustHave`), or as an audit query. Indexed views come first (SQL Server PR 2; planner technique `indexedView`, SQL Server only, not for audit choices): formulaSql's `indexedView` (the `view` of a T-SQL forall result) reads a flat violation query (joins and conditions only: no subqueries, CTEs, outer joins; aliases of one table on the same key merged, else refused as a self-join) as kind `empty` (∀x̄ (φ → ¬ψ), ∀x̄ ¬(φ ∧ ψ): `CREATE VIEW … WITH SCHEMABINDING` of the breaking rows cross-joined with `freefbm_two_rows`, which holds 1 twice, and a unique clustered index on `one`, so any breaking row is refused as a duplicate key, error 2601) or kind `unique` (∀x̄ (φ → ∃^{≤1} ȳ ψ): a GROUP BY view of key and counted columns with COUNT_BIG(*), a unique clustered index on both and a unique index on the key; its key columns are shortened from MAX types); the script then starts with the SET options indexed views need. Unnamed assertions are numbered across views and triggers. The import reads them back (`readIndexedView` in ddlParse.js): an empty view as the assertion NOT EXISTS (its query), a unique one at its unique index on the key, as a count when the counted columns are the counted tables' keys, else as a self-join; `freefbm_two_rows` is dropped. Import (`parseDdl` mode `sqlserver`, `detectDialect`: GO lines, [a].[b], NVARCHAR, (MAX), IDENTITY(…), DATETIME2, UNIQUEIDENTIFIER): GO ends a batch, statements may end without `;` (`tsqlStatements` splits at statement keywords), [names], N'…', 0x… literals, dbo is the default namespace, names keep their declared case (`caseFold`), sqlcmd lines dropped, CREATE TYPE … FROM as a domain, CLUSTERED/NONCLUSTERED, IDENTITY and NEWID()/NEXT VALUE FOR defaults as surrogates, computed columns left out (noted), WITH CHECK/NOCHECK, ALTER COLUMN, SET DATEFORMAT (`tsqlDate`), BULK INSERT skipped, and FreeFBM's own triggers (IF EXISTS (…) THROW/RAISERROR) read back as assertions. FreeFBM's PostgreSQL export reads back the same way: a (constraint) trigger whose PL/pgSQL function raises when IF EXISTS (query) is the assertion NOT EXISTS (query). `sqlserverAssignment` (ddlImport.js) gives each SQL Server type the nearest SQL type (BIT boolean, DATETIME timestamp(3), MONEY numeric(19,4), NVARCHAR(MAX) text, UNIQUEIDENTIFIER uuid, …) and keeps the original in `sqlTypes.sqlserver`. Tested on SQL Server 2022 in a container (Colima profile mssql on Jan's Mac).

Equivalence summary (after formula plan step 4): `src/mapping/equivalence.js` gives one verdict per mapping (`equivalent`, `undecided` or `not`) from four checks: information of each side comes back after a run there and back (per rule, on its pattern's generic population; per entity type that may stand alone, `genericInstance` in accounting.js: tables always, ORM2 types only when independent or playing no other role; plus `uncoveredElements`), and the constraints of each side are kept in the other (constraint accounting). Kept constraints count as graphical unless a formula constraint of the other side is among their keepers; lost ones say whether their translation is a value comparison or a formula constraint (`translateEntry`, `asValueComparison`). Deontic constraints are left out. The Mappings tab's Equivalence button runs it in slices (`EquivalenceReport.jsx`, `store.mappingEquivalence`, not saved; stale once the elements or the mapping change) and also fills `store.mappingAccounting`, so the accounting report below it has the details.

Derived tables and columns (relational Fold plan, part 1): `src/relational/derivedTables.js`. A table of a relational schema keeps rules in `ot.tableRules` (`{ id, name, kind: 'table'|'columns', mode: 'derived'|'semiDerived', body, head }`): the head is a row of the table (`{ [columnFactId]: { k: 'fv'|'opt', y } }`, `$y?` NULL when the optional part $y guards does not match), the body a mapping pattern over the same schema, rows keyed by the table's primary key (all key columns must be in the head). `checkTableRule` runs `checkRule` on the rule as a mapping of the schema onto itself (`tableRuleAsMapping`) plus key/NULL/ownership checks; `compileTableRule` turns it into ordinary derivation rules marked `tableRuleId` (kind table: the table derived through its reference scheme, key values as `ref:i`; each non-key head column a derived fact type, its row role selected and identified by the key, or by the query's own row of the table, its value selected when the query's variable has the column's type, else computed), so populations, validation and the Constraints tab need nothing new; `$y` binds become shared variables (same type) or ≈ (other types). Store actions in mappingSlice (`addTableRule`, `updateTableRule` recompiles in the same step, `addTableRuleColumn` adds a column for a query `$y` with its value type, optionally to the key, `addDerivedTable` from the schema strip's + menu); the rules open in the mapping rule editor (`store.mappingRuleEditor = { tableId, ruleId }`, also in Basic mode, row on top, only its columns editable); the Inspector has a Table rules section, and a derived column shows its rule instead of the derivation radios. Validation lists table-rule issues under Derivation Rules (compiled rules only with errors). The DDL export writes them as views (`src/relational/viewSql.js`, `tableViews`): a table with derived rows (⟺) is `CREATE VIEW t`, one with derived columns or semi-derived rows/columns is stored as `t_base` (fully derived columns left out, semi-derived ones without NOT NULL) and the view `t` reads it (semi-derived rows UNION the query's, derived columns LEFT JOINed by key, semi-derived ones COALESCEd); patterns become FROM/WHERE (opt as LEFT JOIN LATERAL, ¬ as NOT EXISTS), views ordered by what they read, foreign keys only between stored columns. The evaluator binds ∃x̄ over a conjunction with fact atoms through `solve` (first answer) instead of trying every instance.

Fold on the relational side and Refactor (relational Fold plan, part 2): Fold works on compiled table rules as on any derived element: `fragmentOf` reads value joins (`x ≈ y` between variables) as joined slots, a folded table or column is written as a row of its table keyed by its primary key (`ownRow`), identifying facts whose value nothing else uses are dropped from unfolded patterns (`dropBareIdentifiers`), promotion strips `tableRuleId` too (`strip`), the store takes folded elements out of their table rules (`withoutRuleElements` in derivedTables.js) and recompiles, and `suggestedForeignKeys` adds the foreign keys between a folded table and tables with the same key that accounting finds kept (a vertical split gets both directions). `src/mapping/refactor.js`: `cloneSchema` copies a schema with fresh ids (elements, roles, rules, occurrences, populations; `role:<id>` and `_il_` ids remapped), `identityMapping` gives one rule per entity type and non-identifying fact type (fully derived ones left out) from `ownPattern` on both sides; `store.refactorSchema` (schema strip + menu, schemas with fully derived elements) adds the clone and the mapping old → new as one step (the mapping keeps only the rules that change something, see below) and opens the Fold dialog on the clone (`foldDialog: { mappingId, side: 'target', twins }`); folding then deletes the folded elements' twins from the old version, so old → new is checked by the equivalence summary (a vertical split of Chinook's customer is equivalent; a denormalised column is not, until its constraint is added).

Same-model mappings (`src/mapping/sameModel.js`): a mapping between two schemas of one profile (ORM2 → ORM2, relational → relational, as Refactor and the named transformations make) holds only the rules that change something; each element the new version has as it was (entity type or table, non-identifying fact type or column, same name) is a pair in `mapping.unchanged` ([[sourceId, targetId]], saved in the file) instead of a rule copying it to itself. `withImplicitRules(state, mapping)` writes those identity rules out (ids `same_<id>`, marked `identity`, cached) and is applied at the entry points that read a mapping's meaning (prepareRun/runMapping, roundTrip, accountingSteps, equivalenceSteps, planFold, recoverable, foldChanges, suggested constraints and foreign keys, translateEntry, proposeTranslation, proposeCarry, carrySteps, uncoveredElements, exchanges' `stepMapping` and so composed SQL); the Mappings tab (with "n unchanged"), mapping diagrams, Suggest diagrams and rule checks see only the rules. `compactMapping` turns identity rules back into pairs: `_refactor` makes every rule, then refactorSchema, transformSchema (at its end) and foldMapping (unless `compact: false`) compact; loading a file compacts older same-model mappings with `infer` (the element each side of a rule maps).

Named transformations (relational): `src/mapping/transformations.js` lists them (`TRANSFORMATIONS`, each `{ id, label, profile, describe, check, options?, targets?, derive }`): split a table (vertical; chosen columns to a new table keyed by the same key, rows optional), absorb a table whose key is a foreign key to another's key (its columns become columns of that table, the absorbed table dropped when nothing else needs it), foreign key → cross table (a split with required rows), boolean column → table of keys (true rows; a rule gives the false ones). `store.transformSchema(schemaId, id, params)` does it as one undo step: `derive` adds table rules to the old schema, `_refactor` clones it with the identity mapping, extra rules are added, the target side is folded (`planFold`/`foldMapping`, removing what `derive` names when it is recoverable), and `post` carries foreign keys (`carryForeignKeys`) and drops absorbed tables; on error the state is restored. The schema strip's + menu has Transform… for relational schemas (`TransformDialog.jsx`, `store.transformDialog`). Supporting changes: `executeRun(…, { fresh })` gives value variables nothing determines a labelled null (`⊥r…`, used by accounting's back runs) and drops tuples such a null makes redundant (`dropSubsumed`); `recoverable` tries each value of boolean or small value-range types for a labelled null (`finiteCases`); foldMapping deletes subset/equality constraints on removed fact types. Batch 2 edits the new version directly instead of deriving (`edit(api, params, ctx, run)`, for changes no rule can derive): natural key → surrogate (a generated identity column becomes the key, the old key stays UNIQUE, foreign keys to it become one column; rules join to the table through an existential surrogate, which a run invents and `numberInvented` numbers), surrogate → natural key (the old side joins to the table for the natural key, the surrogate becomes a variable there), partition a table by a column with a list of values (one table per value, exclusive keys), merge tables with the same columns (a type column, in the key unless an exclusion makes the keys disjoint), subtype tables → type column, and type column → subtype tables (tables of keys with foreign keys to the table, exclusive). Helpers: `addColumnTo`, `dropColumn`, `setPk`, `addFk`, `addUnique`, `addTable`, `mapRel` (rewrites table row atoms in rule trees), `dropDuplicateRules`. After an edit, transformSchema checks the rules (`checkRule`), carries constraints of the moved elements that the mapping loses as their translations (`carryLost`: accounting for those keys, `proposeTranslation`, added when that keeps them), carries the population by running the mapping, and draws the new constraints between their fact types. Equivalence's info checks and Fold's `recoverable` try each value of a labelled null whose column has a boolean type or a list of values (`finiteCases`, role value ranges and multi-column keys included).

Named transformations (ORM2): the same `edit` path on ORM2 schemas (profile `orm2`; Transform… in the schema strip's + menu for both kinds). Unary → boolean (`E has V`, V ∈ {true, false}, mandatory; rules read U(x) as ∃v (B(x,v) ∧ v ≈ 'true'), a rule gives the false ones), boolean → unary (a binary with two values, mandatory and unique on the entity: one value is the unary, the other its absence), subtype → unary (S's roles move to its supertype with a subset, or an equality when mandatory, into the unary; subtype members of constraints become the unary's role; S-typed variables become E-typed guarded by the unary), unary → subtype (roles with a subset/equality into the unary move to the new subtype), flatten (an objectified fact type F nested as N becomes the entity type N with binaries "N involves Ai", N's role mandatory and unique, identified by F's preferred or first uniqueness constraint over the Ai roles; F(x̄) in rules is ∃n (n involves x1 ∧ …), implied links `F_il_i` are the binaries) and objectify (its reverse; an ∃n with every implied link and nothing else folds back to F(…)). Each rewrites the mapping's target patterns and the new version's formula constraints and derivation rules with the same function, and carries constraints it can't move (several roles of a dropped fact type in one sequence) as formula constraints (`carryFormulas`: the old constraint's formalised formula, `formulaToRule` from src/logic/formulaToRule.js, ids renamed with `renameIds`, rewritten); booleanToUnary turns ∀x (∃ȳ F(…x…) → U(x)) back into subset constraints (`formulasToSubsets`). Ref mode ↔ composite identifier is left out (it needs value functions, decision Q7).

Relational schemas as first-class objects (RM plan, step 1): `src/relational/relationalView.js` (`relationalView(state, schemaId)`, cached) is the relational face of a relational schema that the panels are to read through: each table, view, `<name>_base` stored part, column, NOT NULL, primary key, UNIQUE, foreign key, CHECK and assertion (a constraint with no table form, from formulaSql.js) gets an RM id (`table:<entityId>`, `base:`, `col:<factId>`, `bcol:`, `nn:`, `pk:`, `uq:<ucId>`, `fk:<constraintId>`, `ck:…`, `as:…`), its SQL name, label and text, `enforced`, and `members` (the ORM2 ids it stands for); `ofOrm` maps ORM2 ids back (`rmObjectOf`, `rmLabel` give "film.title", "PRIMARY KEY film_pkey"). It reads the schema as the DDL export does (`tableViews`, `constraintsAsSql`). Key and foreign key names: the DDL import keeps a script's names (`CONSTRAINT x`, unique index names; `sqlName` on internal uniqueness objects, uniqueness and subset constraints), `relationalModel`'s `nameKeys` gives the others PostgreSQL's default (`defaultConstraintName`: `t_pkey`, `t_a_key`, `t_a_fkey`, `t_a_check`; repeated names numbered), and the export writes the script's names back. `node scripts/relational-view-check.mjs file.sql …` checks the view against the export and an export/import round trip (the test schemas are in the project files). Step 2: a relational schema shows its relational face unless its logical view is on (`src/relational/face.js`: `isRelationalFace`, `activeRelationalFace`; `store.logicalViews[schemaId]`, a session setting, set by the Tables | Logical switch right of the diagram tabs, Advanced mode only, `setSchemaLogicalView`). In the relational face the schema browser lists Tables (stored ones, `<name>_base` included), Views and Assertions, each table unfolding into columns, keys, foreign keys and CHECKs (`RelationalBrowser.jsx`, add buttons add the table's entity occurrence, which the ERD draws; no delete), the Inspector shows `RelationalInspector.jsx` (table, view, column, key, FK, CHECK, assertion; read-only; the export's SQL for a table; Transform links that open the Transform dialog preselected, `store.transformDialog = { schemaId, kind, params }`), the tool panel offers only Transform…, and the status bar counts tables, columns and constraints. A relational schema is read-only in both faces (`isReadOnlySchema`/`activeReadOnly` in face.js): the store's `set` drops an update that changes one of its elements other than in position (`refusedEdit` in src/mapping/pairLock.js; x/y at any depth are layout) and sets `store.readOnlyNotice` (status bar), unless it runs in an undo batch (`historyBatch`: transformations, imports, Fold, Guess/Generate), replaces `schemas` (open, delete schema), or comes from an action in `RELATIONAL_EDITS` (ormStore.js: table rules, carried constraints, formula → graphical, populations). The tool panel offers only Transform… in the logical view too. Diagrams of relational schemas (not mapping diagrams) show tables whole (`src/relational/tableUnits.js`): adding the entity type or any column fact type adds the table's entity type, column fact types and value types plus the constraints about shown elements only (`withTableConstraints`: keys, CHECKs, FKs between shown tables), removing any part removes the table (`tableRemoval`; a value type stays while a shown column uses it), opening a file completes partly shown tables (`completeTables` in loadModel), and a transformation completes them on every diagram (`store.completeTableDiagrams`). The logical view (Advanced) draws the side in ORM2 again. Next steps (logical-view layouts and table occurrences) are in the Claude doc "Relational schemas as first-class citizens".

View mappings (data exchange plan, step 1): one-way mappings that define elements of a target schema by queries over a source schema (GAV), in `state.views` (saved as `schema.views`, part of undo, dropped with either schema): `{ id, name, sourceSchemaId, targetSchemaId, rules: [{ id, name, head: { typeId } | { factId }, rule }] }` (`src/mapping/views.js`). A rule has the format of the head's own derivation rule (an entity type through its reference values `ref:i`, a subtype through its subject, a fact type `{ body, extraVars, terms }`) and may read both schemas; variables of the two schemas meet by value (≈). The rules stay out of the target's elements: `viewState` gives a copy of the two schemas with each head derived by its rule and the target's population left out, and with the target's value types open (`openTypes`: the evaluator's `solve` binds a variable of one by ≈ to a value bound already instead of enumerating it; a variable of any other type that x ≈ w ties to a bound variable is looked up in an index of its type's instances by data value, `valueIndex`/`valueKey`, so a selected entity role meets its source variable without a scan). `runView` evaluates it with `withDerivedPopulations` (whose `report` collects errors), `store.applyView` puts the result in the target as one undo step; `checkViewRule` (scope, head, the head's own rule checks) and `viewCoverage` (target elements without a rule: an error for a fact type with a mandatory role, else a warning). The Mappings tab lists views under the two-way mappings (`ViewMappings.jsx`: + Rule for…, Run ⇒, Apply), and rules open in the derivation rule editor's view mode (`openViewRuleEditor`, `ruleEditor = { viewId, ruleId, otId | factId }`; a type whose name occurs in both schemas is written "Artist (source)" / "Artist (target)" in sentences, formulas and palettes: `viewState` and the editor's state carry `schemaRoles` (`schemaRolesOf`), which `makeContext`'s `typeName` and `withSchemaNames` read). Step 2: the Mappings tab shows view rules as sentences, formulas or both (localStorage `freefbm.views.show`), the schema strip lists views with the mappings (⇒ chip), and a view has a diagram like a mapping's (`store.openViewDiagram`; `diagram.mappingId` is the view's id, `mappingOfDiagram` finds views too and `isViewMapping` tells them apart; drawn in ORM2, `viewRuleElements` gives each rule's elements by side, rule nodes ⇒ open the rule editor). Step 3: exchanges (`src/mapping/exchanges.js`, `state.exchanges`, saved as `schema.exchanges`, part of undo): `{ id, name, steps: [{ mappingId, direction }] }`, a chain of two-way mappings (either way) and views (forward only), each step starting where the one before ended (`checkExchange`, `nextSteps` for the + Step menu). `runExchange` runs each step on what the step before left (runMapping or runView, then withRunApplied; invented ⟨…⟩ values of generated columns numbered, `numberInvented`), and checks each schema it fills against its constraints (`resultIssues`: the Validation panel's population checks on that schema; `issueLines` names them, in table terms on a relational schema via `rmViolations`, `groupedLines` puts those of one kind about one element together). `store.applyExchangeRun` puts the last step's population into its schema (one undo step); the ones in between are not kept. A view run is checked the same way. `runView` adds the reference values of the entities it makes to their value types (identifying facts are not stored). `src/relational/populationSql.js` (`populationSql(state, schemaId, { format: 'insert'|'copy' })`) writes a relational schema's rows as INSERT statements or COPY blocks, parents before children (a foreign-key cycle gets deferred constraints), views and fully derived columns left out (`<name>_base` for tables with derived columns), and sequences of generated columns moved past the values written; the exchange report has Export INSERT…/COPY… and File › Export Sample Rows as SQL… writes the active relational schema's. Casts (data operators, group Conversions): asInteger, asDecimal, asFloat, asBoolean, asDate, asDatetime, asTime read a text (or a narrower value) as another datatype, partial; formulaSql writes them as CAST. The `Exchanges.jsx` section of the Mappings tab lists exchanges with their steps, Run, and the per-step report. Step 4, the contract check (`src/mapping/contract.js`): for each constraint of a view's target, whether the source's constraints guarantee it through the views. `mergedState` puts both schemas into one schema (`__contract__`), the target's elements stored, each view rule's formalised formulas (`viewRuleEntries`, `formulaToRule`) as formula constraints `view:<ruleId>:<i>` (so the chase applies both directions as TGDs), plus for a target entity type without a rule of its own `view:produce:<typeId>` (each instance plays a role some fact rule computes, a disjunction); fact types without a rule, and entity types nothing produces, are `empty`. `contractEntry` (accounting.js) builds the smallest violation of the target constraint, rules out one with facts of empty elements, chases first with the view rules and the source's uniqueness constraints only, then with all the source's constraints (the target's own are disabled, their preferred identifiers stay), and gives guaranteed (with the source constraints needed, each left out in turn), mustGuarantee (a chased population that meets the source's constraints; `confirm` runs the views on it, labelled nulls made concrete values of their datatypes, `concrete`, and it counts only when the views really break the constraint) or unknown. `proposeGuarantee` tries a mandatory role or single-role uniqueness on the source fact types the relevant view rules read and keeps the first that makes the constraint guaranteed. The evaluator treats labelled nulls (⊥n) as values equal only to themselves (`varValue` labelled, `compare` in dataOperators.js). The view's Contract button runs `contractSteps` in slices (`ContractReport.jsx`, `store.viewContracts`, not saved): counts, each constraint's sentence and status, the guaranteeing source constraints, counterexamples (source population and what the views make of it), and the proposed source constraint with Add (`store.addSimpleConstraint`). Step 5, composed SQL (`src/mapping/composeSql.js`): `composeExchangeSql(state, ex, { sourceSchema, targetSchema })` writes a chain from a relational schema to a relational schema as one script of `INSERT INTO t (…) WITH k AS (keys), c1 AS (key, value), … SELECT … FROM k LEFT JOIN …` per table of the last schema (FK order), to run on the first schema's database. Each rule of the last step that names a table row (a mapping run into it: its other side with the frontier values as key and columns; a view: its type or column rule) is a query (`{ vars, atoms }`, rule-tree atoms plus `not`/`or`) unfolded back through the steps (`rewrite`): a view replaces target atoms by their rules (selected entity roles add a type atom; an entity type without a rule has the instances its producing fact rules make, a union), a two-way mapping replaces the atoms of the schema it ends in by the other side of their atomic rule (`atomicRules`), identifying facts become ≈ (values meet by value, as in views; composite identifiers are not supported yet), and disjunctions become UNIONs. `simplifyQ` merges ≈-equal variables and rows of one table with the same key (also into a negation), then `formulaToSql` (the query of ∀ō ¬φ; `qualify` prefixes table names with a schema) writes each SELECT. Rules it can't write (optional parts, aggregates, invented keys) are left out with a note. The exchange's "SQL script…" button shows the script with the two schema names and saves it (`ComposedScript` in Exchanges.jsx).

Implicit participation (Halpin) is a real constraint (no entry for a fully derived type whose rule has its subject play a non-identifying role, `derivedPlays`): an instance of an entity type that is not independent plays some role besides its identification (`src/utils/independence.js`: `isIndependentType`, the entity types of a relational schema count as independent since a row may have only its key; `identifiedRoles`). Population validation reports `nonIndependentNotPlaying` (identifying roles don't count), accounting checks the `part:<typeId>` entries of entity types and its chase applies them like an inclusive-or (`participationOf`), Rmap gives no table to a non-independent type that is part of another type's identifier or plays in an objectified fact type, and Guess marks entity types with no mandatory role besides identification independent.

ORM2 auto layout (Auto layout right of the diagram tabs, for any non-ERD, non-mapping diagram; it may move everything): `src/layout/ormLayout.js`. `prepareLayout` collapses reference modes (unless `refModeCollapseBlockers`), merges duplicate occurrences, makes attribute fact types (an entity type and a value type that plays nothing else), unaries and ring fact types satellites of their entity type (rows beside it, each with its own value type occurrence; two columns past 14; a column can hang up or down away from links), lays each subtype tree out as a tidy tree (`layoutTree`; wrapped rows leave a gap in the middle for the links to lower rows), and gives the core graph (blocks, other value types, other fact types as nodes; `finishLayout` builds the diagram: binary role order and orientation per fact type to shorten connectors (any binary may be reversed: the reverse-reading arrow covers it), uniqueness bars on the side without connectors, a satellite unary's reading beside it (`readingOffsetBelow`), external constraints by a cost search over free spots near what they constrain (connector length, crossings with role and subtype lines and other constraints' connectors, connectors through boxes, sitting on a line; Growing diagrams by hand (for large schemas such as an imported AdventureWorks): an object type, objectified fact type or table has Add Neighbours… and New Diagram from Here on its context menu (canvas, ERD table boxes, schema browser rows; not on mapping diagrams). `src/utils/neighbourhood.js` (`neighbourUnits`) lists an element's neighbours as units added whole: in ORM2 each fact type it plays (Attributes when all other players are value types, else Relationships; its reference mode left out) and each subtype link (Subtypes, Supertypes); in a relational schema each table it references or that references it (References, Referenced by; several foreign keys between the same tables are one unit) and each junction table (primary key made of two or more foreign keys) together with its far tables (Many-to-many). Attributes, subtypes and dependants (a referencing table whose foreign key is in its key or is a key, a referenced table this one depends on) are pre-ticked; a unit leading to an element with more than 12 neighbours is marked hub. `NeighbourPicker.jsx` (`store.neighbourPicker`, opened by `openNeighbourPicker`, sits beside the anchor) groups them with checkboxes, a filter, keyboard use (arrows, Space, Enter, Esc), Defaults/All/None/On no diagram, and One more step (the pre-ticked units of what is added). `store.addNeighbours` adds the chosen units as one undo step and places them around the anchor without moving what was there (`src/layout/growPlacement.js`, passed in by the picker because it reads component geometry: `placeOrmUnits` searches directions and rings for free space, a clear line to the anchor first, orients binaries towards the anchor, puts new constraint occurrences near what they constrain and moves internal frequency markers of fact types no other diagram shows; `placeErdUnits` does the same for table boxes, after fixing the shown tables' positions). `store.newDiagramFrom` makes a diagram of the element's schema named after it, centred, with the picker open. Adding neighbours (and Copy/Move to a new diagram) also adds the external constraints that all the diagram's elements now allow and that are about something just added (`withTouchedConstraints` in diagramSlice.js; otherwise constraint occurrences are never added automatically). Growing mode (the Grow switch right of the diagram tabs, `store.growMode`, session only, also on while the picker is open) shows a "+n" badge at each element with n neighbourhood units not on the diagram (`GrowBadges.jsx`, `hiddenNeighbourCounts`; in ErdView at the table boxes), a click opens the picker, and the switch shows how much of the schema some plain diagram shows (`diagramCoverage`: tables, or object and fact types). The multi-selection menu has Copy / Move Selection to New Diagram (`store.selectionToNewDiagram(move)`: a diagram named "<diagram> part n" with the elements where they were; Move takes them off the source except object types a remaining fact type still needs, and fact types the removal cascades off go along). Connect: with two entity types (tables, objectified fact types) multi-selected, or on the context menu of one right after selecting another ("Connect with X", `store.previousSelectedId`), adds the shortest chain of units between them (`connectPath`: Dijkstra over neighbourhood units, not through value types, hubs cost extra; `store.connectElements` → `addNeighbours(…, { given })`, each unit placed beside the element before it). File › Open also accepts NORMA `.orm` files: `src/import/norma.js` (`importNorma`) turns the XML into a FreeFBM model, which opens as a new unsaved model with an import log (`ImportLogPanel.jsx`); `src/import/openModelFile.js` routes the file. Labels NORMA draws as shapes of their own (ReadingShape, ValueConstraintShape, CardinalityConstraintShape, ObjectifiedFactTypeNameShape; role names not yet) keep their place: `src/import/normaLabels.js` (`placeLabel`) keeps the side of the shape a label is on, its gap and how it lines up along that side, measured from FreeFBM's own box and label size, into the occurrence's reading, value range (role and object type) and name offsets. An object type occurrence keeps its own `valueRangeOffset`/`cardinalityRangeOffset` (dragging writes there, `store.updateObjectTypeLayout`; the type's own offsets are the fallback). The Inspector shows a moved label as the Reading Position row does (a read-only Free, Default puts it back on the active diagram): Name Position for an objectified fact type's name (`nameOffset`), and Position in the value and cardinality range inspectors (`store.rangeLabelMoved`/`resetRangeLabel`). NORMA role paths (derivation rules of fact types and subtypes, hand-drawn join paths) become rule-tree formulas via `src/import/normaPaths.js`; positive linear self-recursion in a fully derived fact type's rule is rewritten as a TC* closure (`closeLinearRecursion`). Calculated values apply the model's own functions, read by operator symbol or name (`FUNCTIONS`: comparisons, connectives, data operators and predicates): a lead path's Conditions become conditions at the innermost scope binding their objects, a projected calculated value or constant the term of a computed role; aggregates, unknown functions, outer joins, subqueries and shared paths are refused with a reason in the import log. A subpath with its own RootObjectType starts from a new object; CorrelatedWith unifies like an ObjectUnifier. An objectified old-style unary's link fact type has an ObjectifiedUnaryRole where others have a RoleProxy; it is read the same way. A path through an old-style unary (a binary with an implicit boolean value type) is a path through the unary: it may start at the boolean value and enter the unary through it, a test for true gives F(x) and a test for false alone ¬F(x) (literally it matches nothing; noted in the element's note and the import log). Informal rules (InformalRule/DerivationNote, the older DerivationExpression) are kept in the element's note. Import notes (`src/utils/importNotes.js`): what the import adapted is kept on the element it is about as `importNotes: [{ id, severity, text }]` (saved in the file), severity `changed` (meaning changed or lost, violet) or `rewritten` (same meaning, slate); a constraint the import leaves out puts its note on the elements it named. They show as a ✎ badge at an element's bottom-right corner (`ImportNoteBadges` in Canvas.jsx; hover lists them, a click selects), in the Inspector (`ImportNotesSection`: Dismiss removes one, undoable, `store.dismissImportNote`; Show on diagram adds a coloured diagram note linked to the element, `store.showImportNoteOnDiagram`, note `importNote: { severity, elementId, noteId }`, coloured by NoteNode) and under Import in the Validation panel. An external uniqueness constraint over an old-style unary F's boolean role reads that role as the condition F(t): when F is mandatory it is left out (an internal UC when the rest is one fact type, preferred identifier kept), else the constraint becomes a uniqueness over a join query with F(t), no longer a preferred identifier (`qualifiedUniqueness`, `conditionalQuery`; `joinQuery` positions may be 'drop'). Negatable unaries of current NORMA (UnaryPattern, NegatedByUnaryFactType): the pair stays two unaries read under the closed-world assumption ("is known to …", "is known not to …") with NORMA's exclusion or exclusive-or; a negation without a reading gets the positive one plus "(negation)", default values are dropped, and a rule or join path negating such a unary is flagged, all as import notes. Date and time bounds of value ranges: NORMA keeps them as typed (no invariant form for temporal types; .NET `DateTime.TryParse`, e.g. `1900/01/01`, `1/31/1900`, `31 January 1900`), and `src/import/normaTemporal.js` rewrites them in XML Schema's form (month first when the order is open, as NORMA compares bounds in the invariant culture; a rewritten import note, a changed one when ambiguous). Semi-derived rules may use themselves positively (least fixpoint over the stored population, `derivedPopulation.js`).

Population validation coverage: `node scripts/population-coverage-check.mjs [--runs N] [--seed S] [--verbose] [file.ffbm …]` checks that population validation (`computePopulationIssues` plus the derived-population checks, as `runValidation` runs them) reports an issue about a constraint exactly when the constraint's formula (`formalise` whole schema and the implicit participation entries, evaluated by `closedFormula` via `formulaToRule`) is false, on the stored population and on N mutated ones (tuples and instances removed, added or changed, structural issues then repaired by removing what they name). Without files it uses the sample and the variants in `scripts/coverage-fixtures.mjs` (cardinality ranges, join-path and implied-link or-constraints, cross-fact value comparison and frequency, all ring kinds, deontic constraints, constraints without queries). It reports unchecked entries, missed violations, false alarms, deontic marking errors and unknown issue kinds (each kind is either about a constraint or in its STRUCTURAL list); entries without a formula (no join path yet) are listed but not tested. Cardinality ranges are checked as `cardinalityViolation` (type: distinct instances with subtypes; role: distinct players); inclusive-/exclusive-or read each sequence through its query, and skip a constraint whose sequence can't be read. `formulaToRule` turns counts of several variables with bounds 0 and 1 (an external preferred identifier's "exactly one combination") into ∃ and ¬∃ȳȳ' (φ ∧ φ' ∧ ȳ ≠ ȳ').

### Styling

`src/index.css` defines CSS custom properties for the entire design system (parchment/navy palette, ORM2 element colours, fonts). Components use these variables directly — no CSS-in-JS or utility framework.

Fonts are bundled (`@fontsource/*`, imported in `src/main.jsx`; the CSP allows no remote fonts): `--font-ui` (IBM Plex Sans) for the whole interface, `--font-mono` (IBM Plex Mono) for formulas, SQL, datatypes and ids, `--font-display` (Fraunces) for the logo. Diagram drawings keep their own Segoe UI stack (measured for layout and NORMA labels). Controls in the bars above the canvas use `.ui-btn` (index.css): an action is a button, an on/off mode a button with `aria-pressed`, a menu ends in `.ui-caret` ▾, and a choice between states is a segmented control; links only go somewhere.
